# Модульное рабочее пространство (VERM)

Единое модульное рабочее пространство на Python с графическим интерфейсом, предназначенное для работы с данными маркетплейса **Wildberries**: выгрузка карточек товаров, характеристик и ведение локальной базы данных. Начата подготовка интеграции с **Ozon** (добавлено хранение мастер-токена).

---

## 🚀 О проекте

Проект представляет собой **модульный лаунчер** с графическим интерфейсом на базе [CustomTkinter](https://github.com/TomSchimansky/CustomTkinter). При запуске приложение автоматически сканирует папку `apps/`, находит все модули (Python-скрипты) и строит под них интерфейс в виде кнопок. Каждый модуль можно запустить одним кликом — выполнение происходит в отдельном фоновом потоке, поэтому интерфейс не «зависает» во время длительных операций (например, выгрузки данных из API).

### Ключевые архитектурные особенности

| Особенность | Описание |
| --- | --- |
| 🧩 **Модульность** | Любая новая функция добавляется как отдельный скрипт в `apps/` — лаунчер подхватывает её автоматически, без правки самого лаунчера. |
| 🐍 **Общее виртуальное окружение** | Все модули используют единый интерпретатор и зависимости из `.venv/` (см. `requirements.txt`). |
| 🗄️ **Единое хранилище данных** | Все данные, логи и служебные файлы хранятся в одном месте — каталоге `data/`. |
| 🧵 **Фоновые потоки** | Модули запускаются в отдельных потоках; обновление GUI безопасно выполняется только из главного потока через очередь сообщений. |
| 🔐 **Секреты в `.env`** | 8 токенов Wildberries (1 мастер + 7 специализированных), мастер-токен Ozon (`OZ_MASTER_TOKEN`), а также параметры складов (`WB_WAREHOUSE_ID`, `OZON_WAREHOUSE_ID`) и `OZON_CLIENT_ID` хранятся в корневом файле `.env`, который не попадает в Git. |
| ⏱️ **Rate Limiter** | Встроенный Token Bucket (`WBRateLimiter`) ограничивает частоту запросов по категориям API и защищает от HTTP 429. |

## 💻 Текущий функционал системы

### Ядро (лаунчер) — `main.py`

Лаунчер отвечает за **обнаружение и запуск модулей**, а также за построение интерфейса.

**Возможности ядра:**

- **Динамическое сканирование модулей.** Функция `discover_modules()` просматривает каталог `apps/` на наличие файлов `*.py`, игнорируя `__init__.py` и служебные файлы, чьи имена начинаются с `_`. Результат сортируется по алфавиту.
- **Автоматическое построение интерфейса.** Для каждого найденного модуля создаётся кнопка в прокручиваемом списке; подпись кнопки формируется из имени файла (символы `_` заменяются на пробел, применяется заглавный регистр). Кнопка «Обновить список» позволяет пересканировать каталог без перезапуска.
- **Запуск скриптов в фоновых потоках.** При нажатии кнопка блокируется (переходит в состояние «выполняется…»), а модуль запускается в отдельном `threading.Thread`. Модуль должен содержать вызываемую функцию `run()`.
- **Потокобезопасное обновление GUI.** Так как Tkinter/CustomTkinter не потокобезопасны, рабочий поток передаёт результат в главный поток через `queue.Queue`; интерфейс опрашивает очередь каждые 100 мс (`_poll_queue`). Это исключает зависание и «креш» интерфейса.
- **Повторный запуск с перезагрузкой.** Если модуль уже импортирован, при повторном запуске он перезагружается через `importlib.reload()`, чтобы подхватывались свежие правки кода.
- **Гибкая настройка.** Параметры внешнего вида (тема оформления, цветовая схема, размер окна) читаются из `data/config.json` и имеют значения по умолчанию. Переключатель «Тёмная тема» меняет тему на лету.
- **Автозапуск и таймер модуля DBase.** Если в конфиге включён параметр `dbase_auto_start`, при старте лаунчер автоматически запускает модуль `DBase.py` (имитируя нажатие кнопки). Далее модуль циклично перезапускается через `root.after()` с интервалом `dbase_interval_minutes`. Если модуль в этот момент ещё выполняется, таймер пропускает цикл и не запускает параллельную копию.
- **Кнопка полного обновления БД.** Рядом с кнопкой «D Base» расположена квадратная кнопка «🔄» (две закруглённые стрелки — значок обновления). Она удаляет файл курсора `data/wb_cards_cursor.json` и запускает полную выгрузку каталога заново (служебный модуль `apps/_Full_Update.py`), предварительно запросив подтверждение.
- **Настройки таймера.** Рядом с кнопкой «D Base» (справа от «🔄») расположена кнопка «⚙️», открывающая модальное окно (`ctk.CTkToplevel`), где можно включить/выключить автозапуск и изменить интервал обновления в минутах. Сохранение перезаписывает `data/config.json` и сразу перенастраивает активный таймер под новый интервал.
- **Настройки токенов и параметров API.** В том же окне настроек есть прокручиваемые секции «Токены WB API» (8 полей), «Токены Ozon API» (поле `OZ_MASTER_TOKEN`) и «Параметры API» (`WB_WAREHOUSE_ID`, `OZON_WAREHOUSE_ID`, `OZON_CLIENT_ID`). При сохранении значения перезаписываются в файл `.env`, а пустые специализированные токены WB автоматически откатываются на мастер-токен через `get_wb_token(category)`.

### 🔐 Управление токенами и параметрами (Wildberries и Ozon)

Проект хранит токены и параметры API в корневом файле `.env`, а единая логика чтения реализована в `apps/DBase.py`.

**Wildberries** — гибкое распределение лимитов запросов по категориям методов:

- **`get_wb_token(category)`** — возвращает токен для категории (`CONTENT`, `PRICES`, `STOCKS`, `MARKETPLACE`, `STATISTICS`, `PROMOTION`, `FEEDBACKS`). Если специализированный токен не заполнен, автоматически возвращается мастер-токен.
- **Мастер-токен (`WB_MASTER_TOKEN`)** — резервный токен для всех категорий. Для обратной совместимости старый ключ `WB_API_KEY` также воспринимается как мастер-токен.
- **8 полей токенов:** `WB_MASTER_TOKEN`, `WB_TOKEN_CONTENT`, `WB_TOKEN_PRICES`, `WB_TOKEN_STOCKS`, `WB_TOKEN_MARKETPLACE`, `WB_TOKEN_STATISTICS`, `WB_TOKEN_PROMOTION`, `WB_TOKEN_FEEDBACKS`.

**Ozon** — на начальном этапе интеграции:

- **`get_oz_token(category)`** — возвращает токен Ozon для категории методов (пока доступна только `MASTER`).
- **`OZ_MASTER_TOKEN`** — мастер-токен Ozon, единственное поле Ozon на данный момент (остальные токены будут разделены позже, когда станет понятно, какие из них нужны).

**Параметры API (не токены):**

- **`WB_WAREHOUSE_ID`** — массив ID складов Wildberries. Формат: JSON-массив (например `"[37356, 12345]"`) или перечисление через запятую. Читается через `get_wb_warehouse_ids()`.
- **`OZON_WAREHOUSE_ID`** — массив ID складов Ozon (аналогичный формат). Читается через `get_oz_warehouse_ids()`.
- **`OZON_CLIENT_ID`** — Client-Id продавца Ozon. Читается через `get_oz_client_id()`.

**Графическое управление.** В окне настроек лаунчера (кнопка «⚙️») доступны прокручиваемые секции «Токены WB API» (8 полей), «Токены Ozon API» (поле `OZ_MASTER_TOKEN`) и «Параметры API» (`WB_WAREHOUSE_ID`, `OZON_WAREHOUSE_ID`, `OZON_CLIENT_ID`); все значения можно отредактировать и сохранить обратно в `.env` (вставка значения — через `Ctrl+V` / `Ctrl+М` в русской раскладке).

### ⏱️ Rate Limiter (Token Bucket)

Для защиты от ошибок HTTP 429 (`Too Many Requests`) в `apps/DBase.py` реализован встроенный многопоточный ограничитель запросов **`WBRateLimiter`** на базе алгоритма **Token Bucket** («маркерная корзина»).

**Принцип работы:**

1. Для каждой категории API (`CONTENT`, `PRICES`, `STOCKS`, `MARKETPLACE`, `STATISTICS`, `PROMOTION`, `FEEDBACKS`) создаётся независимая «корзина» токенов.
2. Каждая корзина описывается двумя параметрами:
   - **`max_tokens`** — ёмкость корзины (допустимый всплеск/burst запросов);
   - **`refill_rate`** — скорость пополнения (сколько токенов добавляется в секунду).
3. Перед каждым HTTP-запросом к Wildberries рабочий поток вызывает **`limiter.wait_for_token(category)`**:
   - если в корзине есть токен — он забирается и запрос выполняется сразу;
   - если токенов нет — поток вычисляет время до появления следующего токена и блокируется через `time.sleep()`, мягко приостанавливая выгрузку до безопасного момента.
4. Все корзины потокобезопасны: каждая защищена `threading.Lock`, поэтому несколько фоновых потоков (модулей) не конфликтуют между собой.

**Лимиты по умолчанию (согласно документации Wildberries):**

| Категория | Лимит | `max_tokens` (burst) | `refill_rate` |
| --- | --- | --- | --- |
| `CONTENT` | 100 запросов/мин (~600 мс) | 5 | ~1.667 ток/сек |
| `PRICES` | 3 запроса/сек (~333 мс) | 3 | 3 ток/сек |
| `STOCKS` | 5 запросов/сек (~200 мс) | 5 | 5 ток/сек |
| `MARKETPLACE`, `STATISTICS`, `PROMOTION`, `FEEDBACKS` | базовый безопасный лимит | 2 | 2 ток/сек |

Глобальный экземпляр `LIMITER` доступен всем модулям через `apps.DBase`; модули `DBase.py` и `Stack.py` вызывают `wait_for_token("CONTENT")` перед каждым запросом к Content API вместо жёстких `time.sleep(0.6)`.

### Подключённые модули

Сейчас в каталоге `apps/` физически находятся **два модуля**:

#### 📦 `DBase.py` — база данных и интеграция с Wildberries Content API v2

Модуль `DBase` — **единственная точка управления схемой базы данных** проекта. Только ему разрешено создавать, изменять или удалять таблицы и колонки SQLite-базы `data/inventory.db`; все остальные модули могут лишь читать, добавлять или обновлять строки.

**Что делает модуль при запуске (монолитный алгоритм инициализации):**

1. **Проверка токена.** Получает токен категории `CONTENT` через `get_wb_token("CONTENT")` из файла `.env`. Если файл отсутствует — создаёт его с шаблоном из полей WB и Ozon; если специализированный токен пуст, используется `WB_MASTER_TOKEN` (fallback), а при его отсутствии — завершает работу с сообщением об ошибке.
2. **Создание/обновление схемы БД.** Создаёт таблицы, при необходимости мигрирует структуру `wb_products` и добавляет колонки в `wb_charcs`, создаёт частичные уникальные индексы и наполняет справочник `wb_charcs` базовым маппингом (Seed).
3. **Выгрузка карточек товаров.** Обращается к `POST /content/v2/get/cards/list`, с пагинацией курсором выкачивает все карточки и раскладывает их по таблицам:
   - корневые («паспортные») параметры → `wb_products`;
   - динамические характеристики (паттерн EAV) и вложенные объекты (`photos`, `documents`) → `wb_product_values`.
4. **Синхронизация справочника характеристик.** По уникальным категориям товаров опрашивает `GET /content/v2/object/charcs/{subjectId}` и заполняет таблицу `wb_charcs` шаблонами полей.

**С какими данными работает модуль:**

| Таблица | Назначение |
| --- | --- |
| `brands` | Справочник брендов: юридическое название, названия на WB/Ozon, альтернативные имена для поиска, страна. |
| `status` | Составной ключ товара `UNIQUE(ART, SUP)` (артикул + буквенный суффикс поставщика). |
| `wb_products` | «Паспорт» товара — корневые параметры карточки: наименование, бренд, габариты, вес, `vendorCode`, `nmID`, `imtID`, `subjectID`, `chrtID`/`skus`/`techSize`/`wbSize` (из массива `sizes`). Новые скалярные поля из ответа API добавляются в таблицу автоматически. |
| `wb_product_values` | Значения (EAV): характеристики `ART + SUP + charcID → value`, а также универсальные вложенные поля `ART + SUP + field_name → value` (например, `photos` и `documents` хранятся здесь как JSON с полной структурой). |
| `wb_charcs` | Справочник характеристик Wildberries: `charcID`, русское название, признак обязательности, признак наличия именованного поля, ключ JSON-маппинга и связь с категориями (`subj_ID`, `subj_NM`). |

**Ключевые технические детали:**

- **Извлечение ART/SUP.** Из строки `vendorCode` регулярными выражениями выделяется ведущая цифровая часть — артикул `ART`, и буквенный остаток поставщика — `SUP`.
- **Инкрементальная выгрузка.** Курсор последней выгрузки сохраняется в `data/wb_cards_cursor.json`, поэтому повторные запуски скачивают только созданные/обновлённые карточки, а не весь каталог заново.
- **Уважение к лимитам API.** Пауза `0.6 с` между запросами карточек и `1 с` между опросами категорий, плюс ретраи при `HTTP 429` и сетевых ошибках (до 3 попыток).
- **Колонки `price`/`cost`** в `wb_products` не заполняются самим `DBase` — они предназначены для заполнения другими модулями (например, модулем цен), чтобы не затирать уже загруженные значения.
- **Безопасный fallback курсора.** Если запрос карточек по связке `updatedAt + nmID` возвращает ошибку, модуль стирает `nmID` и повторяет запрос только по `updatedAt` — это обходит случаи, когда Wildberries отклоняет курсор с устаревшим `nmID`.
- **Очистка «хвостов» EAV.** Перед записью динамических характеристик изменённой карточки модуль выполняет `DELETE` старых значений в `wb_product_values` по связке `ART + SUP`, после чего записывает актуальные значения чистым `INSERT`. Это удаляет характеристики, которых больше нет в карточке WB.
- **Саморасширяемая схема.** При получении ответа `DBase` сам распознаёт новые данные: неизвестные скалярные поля верхнего уровня автоматически создают колонки в `wb_products` (с подбором SQL-типа), а вложенные объекты/массивы (`documents` и любые будущие) автоматически пишутся строками в `wb_product_values` (колонка `field_name`, значение — JSON). Это защищает от нововведений со стороны платформы WB без правки кода.
- **Очистка устаревших колонок.** Колонки, выведенные из схемы (например, старая `Photos`), удаляются автоматически через `ALTER TABLE DROP COLUMN` (список `OBSOLETE_PRODUCT_COLUMNS`); колонки, добавленные под новые поля API (например, `video`), при этом сохраняются.

#### 🔗 `Stack.py` — объединение и разъединение карточек товаров (moveNm)

Модуль `Stack` управляет группами карточек Wildberries через метод Content API `POST /content/v2/cards/moveNm`: объединяет карточки в одну группу (один `imtID`) и разъединяет их, создавая новые группы.

**Что делает модуль при запуске:**

1. **Обновление базы данных.** Первым делом вызывает `apps.DBase.run()`, чтобы актуализировать локальную базу `data/inventory.db` по курсору и подтянуть карточки, созданные продавцом только что.
2. **Поиск по артикулу.** В графическом окне (на `ctk.CTkToplevel`, наследует тему лаунчера) есть поле ввода `vendorCode`. Поиск выполняется напрямую по SQLite-таблице `wb_products`. Если введён только числовой `ART`, а в базе есть несколько карточек с одним артикулом, но разными буквенными суффиксами `SUP`, модуль автоматически добавляет **все** найденные `nmID` в рабочий список.
3. **Контроль состава списка.** Все добавляемые карточки должны относиться к одному предмету (`subjectID`); карточки другого предмета пропускаются с предупреждением. Счётчик следит за лимитом Wildberries — не более **30** карточек за одну операцию.

**Операции с группами (через `POST /content/v2/cards/moveNm`):**

| Кнопка | Тело запроса | Результат |
| --- | --- | --- |
| **Объединить** | `{ "targetIMT": <imtID первой карточки>, "nmIDs": [...] }` | Все выбранные `nmID` объединяются в группу с указанным `imtID`. |
| **Разъединить в новую группу** | `{ "nmIDs": [...] }` (без `targetIMT`) | Выбранные карточки получают один общий новый `imtID`. |
| **Разъединить поштучно (Уникализировать)** | по одному `{ "nmIDs": [<nmID>] }` за запрос | Каждая карточка получает уникальный `imtID`. |

**Ключевые технические детали:**

- **Источник данных.** Модуль полностью работает с SQLite-базой `data/inventory.db` (таблица `wb_products`): `vendorCode`, `nmID`, `imtID`, `subjectID`, наименование. Файлы `settings.json` и `cards.json` не используются.
- **Ключ API.** Токен категории `CONTENT` читается из общего файла `.env` через `DBase.get_wb_token("CONTENT")` с fallback на мастер-токен.
- **Соблюдение Rate-limit.** Поштучное разъединение отправляет запросы последовательно с паузой **600 мс** между ними, не нарушая лимиты контент-API (100 запросов/мин).
- **Обработка ошибок.** Все сетевые запросы обёрнуты в обработку `requests.RequestException`; результаты и ошибки показываются через `messagebox`.
- **Потокобезопасность.** Окно создаётся на главном потоке через `root.after(...)`, а сетевые операции выполняются в фоновых потоках — интерфейс не блокируется.
- **Ввод штрихкодов.** Штрихкод можно вставить из буфера обмена сочетанием `Ctrl+V` (или `Ctrl+М` в русской раскладке); после ввода поле автоматически очищается для следующего штрихкода.

#### 🔄 Полное обновление базы данных (`_Full_Update.py`)

Служебный модуль `_Full_Update` (имя файла начинается с `_`, поэтому он не показывается отдельной кнопкой в списке модулей) удаляет сохранённый курсор инкрементальной выгрузки и запускает полную выгрузку каталога Wildberries заново. Запускается квадратной кнопкой «🔄» рядом с «D Base» в лаунчере.

**Что делает модуль при запуске:**

1. **Запрос подтверждения.** Через диалоговое окно спрашивает, действительно ли нужно удалить курсор и перескачать все карточки (при запуске без лаунчера — через консоль).
2. **Удаление курсора.** Удаляет `data/wb_cards_cursor.json`, чтобы следующая выгрузка была полной, а не инкрементальной.
3. **Полное обновление БД.** Вызывает `apps.DBase.run()` — все карточки товаров и характеристики скачиваются заново целиком.

**Когда использовать:** после изменения схемы БД, добавления новых полей или когда нужно гарантированно перечитать весь каталог (обычный запуск `DBase` подтягивает только созданные/обновлённые карточки).

**Ключевые технические детали:**

- **Источник данных.** Использует общий путь курсора `DBase.CARDS_CURSOR_PATH` и метод `DBase.run()`.
- **Потокобезопасность.** Диалог подтверждения и сообщение о завершении показываются на главном потоке через `root.after(...)`, а само обновление выполняется в фоновом потоке лаунчера.

### Пошаговый гайд (Windows)

1. **Склонируйте/скопируйте проект** в нужную папку и перейдите в неё:

   WB_TOKEN_STOCKS=""
   WB_TOKEN_MARKETPLACE=""
   WB_TOKEN_STATISTICS=""
   WB_TOKEN_PROMOTION=""
   WB_TOKEN_FEEDBACKS=""
   OZ_MASTER_TOKEN=""

   Замените `ВАШ_ТОКЕН_ЗДЕСЬ` на реальный мастер-токен (его можно получить в личном кабинете Wildberries → раздел «Контент» → API). Специализированные токены WB можно оставить пустыми — тогда для них автоматически будет использоваться `WB_MASTER_TOKEN`. `WB_WAREHOUSE_ID` и `OZON_WAREHOUSE_ID` задаются в виде JSON-массива (например `"[37356, 12345]"`) или перечислением через запятую. ## ➕ Инструкция по добавлению новых модулей

Чтобы лаунчер корректно обнаружил и запустил новый скрипт, он должен лежать в папке `apps/` и соответствовать простым правилам:

1. Имя файла — `*.py`, **не** `__init__.py` и **не** начинается с символа `_`.
2. В модуле обязательно должна быть объявлена вызываемая функция **`run()`** — именно её лаунчер вызывает в фоновом потоке.
3. Модуль выполняется в отдельном потоке и **не должен** напрямую обращаться к GUI (Tkinter/CustomTkinter не потокобезопасны).
4. Все выходные файлы, логи и кэши модуль должен сохранять **только** в каталог `data/`.
5. Изменять схему базы данных (создавать/менять таблицы и колонки) может **только** `apps/DBase.py`; остальные модули работают только со строками данных.
6. Если модулю нужна новая библиотека — сначала добавьте её в `requirements.txt` и установите через `.venv\Scripts\pip.exe install -r requirements.txt`.

### Минимальный шаблон модуля

```python
import time
import logging


def run() -> None:
    """
    Главная точка входа модуля.
    Вызывается лаунчером в отдельном фоновом потоке.
    """
    print("[Мой модуль] Started execution...")

    # Здесь — логика вашего модуля
    # (выгрузка данных, обработка, запись в data/ и т.д.)

    print("[Мой модуль] Finished successfully.")


if __name__ == "__main__":
    # Позволяет запускать модуль и напрямую: python apps/имя_модуля.py
    run()
```

### Пошаговый пример

1. Создайте файл `apps/MyModule.py` с кодом выше.
2. Замените логику внутри `run()` на нужную.
3. В лаунчере нажмите кнопку **«Обновить список»** (или перезапустите приложение).
4. Появится кнопка **«My Module»** — нажмите её для запуска.

Готово! Лаунчер автоматически импортирует модуль как `apps.MyModule`, вызовет его функцию `run()` в отдельном потоке и покажет статус выполнения в нижней строке окна.
